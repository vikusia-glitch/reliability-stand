# Стенд надёжности

Маленький сервис, который умеет ломаться по команде, и полный SRE-обвес
вокруг него: SLI и SLO, алерты по скорости сгорания бюджета ошибок,
дашборд по четырём золотым сигналам, ранбуки и постмортем. Весь стенд
разворачивается одним прогоном Ansible.

Смысл проекта не в сервисе. Смысл в том, что происходит, когда сервис
ломается: сработал алерт → дежурный открыл ранбук → починил → написал
разбор с цифрами. Сервис здесь — управляемый источник аварий.

## Что внутри

```
service/     подопытный сервис на FastAPI + тесты
deploy/      docker compose: сервис, Prometheus, Grafana
  prometheus/rules/slo.yml   правила SLI и алерты по burn rate
  grafana/dashboards/        дашборд «Стенд надёжности — SLO»
  prometheus/tests/slo_test.yml  тесты самих алертов
stand.py     кроссплатформенный CLI (macOS, Linux, Windows)
tools/       контейнер с Python, promtool и Ansible
.github/     CI: тесты, правила алертов, подъём стенда с нуля
ansible/     развёртывание стенда с нуля, три роли
loadgen/     генератор фоновой нагрузки
runbooks/    что делать по каждому алерту
SLO.md       показатели, цели, бюджет ошибок и обоснование выбора
POSTMORTEM.md шаблон разбора инцидента
```

## Требования

На хосте нужен **только Docker**. Python, promtool и Ansible ставить не
обязательно: всё это лежит в контейнере с инструментами (`tools/`).

| Что                  | macOS          | Linux               | Windows        |
|----------------------|----------------|---------------------|----------------|
| Стенд                | Docker Desktop | docker-ce + compose | Docker Desktop |
| Тесты, promtool, Ansible | в контейнере `toolbox` | то же | то же |
| CLI `stand.py`       | Python 3.9+, опционально | то же    | то же          |

Образы многоархитектурные, платформа нигде не прибита — на Apple
Silicon всё собирается нативно под arm64.

Порты вынесены в `deploy/.env` (см. `.env.example`): 3000 и 8000 на
чужой машине заняты чаще, чем свободны.

CLI `stand.py` написан на голой стандартной библиотеке — ни curl, ни
make, ни bash не нужны, работает и в PowerShell. Но он не обязателен:
всё то же самое делается напрямую через `docker compose`.

## Быстрый старт

```bash
python stand.py doctor   # проверить, что окружение готово
python stand.py up       # поднять сервис, Prometheus и Grafana
python stand.py test     # тесты сервиса
python stand.py check-rules   # проверить правила алертов
python stand.py load     # фоновая нагрузка 20 rps на 10 минут
```

В Unix то же самое короче: `make up`, `make test`, `make load`.
В PowerShell — `python stand.py ...`, команды одинаковые.

## Совсем без локального Python

Всё то же самое через контейнер с инструментами. На хосте — только Docker.

```bash
cd deploy
docker compose --profile tools run --rm tests         # тесты сервиса
docker compose --profile tools run --rm check-rules   # правила алертов
docker compose --profile tools run --rm loadgen       # нагрузка
docker compose --profile tools run --rm toolbox       # оболочка с ansible и promtool
```

Внутри `toolbox` есть Python с зависимостями, promtool и Ansible.
Чего внутри него делать нельзя — запускать сам `docker compose`:
пути в бинд-монтированиях этого файла разрешает демон на хосте,
и изнутри контейнера они не совпадут. Поднимать и гасить стенд — с хоста.

- сервис — http://localhost:8000/work
- метрики — http://localhost:8000/metrics
- Prometheus — http://localhost:9090 (вкладка Alerts)
- Grafana — http://localhost:3000, логин `admin`, пароль из
  `GRAFANA_PASSWORD` (по умолчанию `admin`)

## Развёртывание через Ansible

```bash
cd ansible
ansible-galaxy collection install -r requirements.yml
ansible-playbook site.yml            # первый прогон
ansible-playbook site.yml            # второй прогон: changed=0
```

Второй прогон без изменений — это и есть проверка идемпотентности,
главное свойство инфраструктуры как кода. Роли: `base` (пакеты,
каталоги, лимит журнала), `docker` (репозиторий, установка, лимиты
логов контейнеров), `stand` (доставка исходников, compose, проверка
живости).

Инвентарь по умолчанию указывает на `localhost`. Для отдельной машины
раскомментировать строку в `ansible/inventory.ini`.

## Управление неисправностью

```bash
python stand.py break --error-rate 0.10    # 10% ответов станут пятисотками
python stand.py break --latency-ms 400     # +400 мс к каждому ответу
python stand.py status                     # что выкручено сейчас
python stand.py heal                       # вернуть как было
```

Под капотом — ручка `/fault`:

```bash
curl -X POST localhost:8000/fault \
  -H 'content-type: application/json' \
  -d '{"error_rate":0.10,"extra_latency_ms":0}'
```

## Учение

Полный цикл, ради которого всё и делалось. Занимает минут двадцать.

1. Поднять стенд и запустить нагрузку: `python stand.py up`, затем
   `python stand.py load` в отдельном окне. Дать ей поработать 5–10 минут, чтобы у SLI
   появился знаменатель.
2. Открыть Grafana и Prometheus → Alerts, запомнить время.
3. Сломать: `make break`.
4. Дождаться `StandErrorBudgetFastBurn`. Ожидаемо — несколько минут:
   короткое окно 5 минут плюс `for: 2m`.
5. Дальше действовать по ранбуку, а не по памяти. Ранбук проверяется
   ровно в этот момент: если в нём не хватает команды — это находка.
6. Починить: `python stand.py heal`.
7. Заполнить `POSTMORTEM.md`: таймлайн по минутам, сколько бюджета
   сожжено, что в ранбуке оказалось лишним или недостающим.

Отдельно стоит проверить `StandDown`: погасить сервис через
`docker stop stand-app` и убедиться, что алерт приходит, а остальные
при этом замолкают.

## Почему так, а не иначе

**Алерты по симптомам, а не по ресурсам.** Загрузка процессора ничего
не говорит о том, что чувствует пользователь. Здесь сигналы — ошибки
и задержка, то есть ровно то, что он видит.

**Два окна в каждом алерте.** Длинное подтверждает, что проблема
настоящая, короткое — что она всё ещё идёт. С одним длинным окном алерт
горит часами после починки; с одним коротким срабатывает на каждый
всплеск, и его перестают читать.

**Метрики снимаются в middleware.** Если считать внутри обработчика,
в статистику не попадут ответы, до него не дошедшие, и SLI будет
оптимистичнее реальности.

**Порог 300 мс — отдельная корзина гистограммы.** Иначе долю быстрых
ответов пришлось бы интерполировать между корзинами.

**SLO 99%, а не 99.9%.** Стенд одноинстансный, без резервирования.
Недостижимое SLO держит бюджет в вечном минусе, и механизм перестаёт
работать.

**`StandDown` — единственный алерт по причине.** Когда метрик нет,
все остальные правила молчат, и тишина выглядит как здоровье.

**Правила алертов покрыты тестами.** Сломанное правило не падает —
оно молчит, и это обнаруживается в момент, когда оно было нужнее всего.
`deploy/prometheus/tests/slo_test.yml` проверяет, что алерт срабатывает
на аварии, молчит на здоровом трафике и — отдельно — молчит при нулевом
трафике, где без защиты знаменателя было бы деление на ноль.

## Чего здесь нет

Alertmanager и маршрутизации оповещений, трейсинга, нескольких
инстансов и балансировки, раздельных SLO по ручкам. Всё это осознанно
за периметром: стенд должен показывать цикл работы с надёжностью,
а не изображать продакшен.
